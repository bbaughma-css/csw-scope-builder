Secure Workload Scope Builder: Customer Guide

Version 1.2, 19 Nov 2026. Supersedes: 1.1.

Your Cisco contact sent you two files with this guide. Together they are used to design and build the scope tree in your Cisco Secure Workload tenant. You run both yourself. Cisco never needs a login or an API key for your tenant.

Part 1. Fill Out The Questionnaire

  1. Save interview.html to your computer and double-click it. It opens in your web browser.
  2. Answer what you know and leave out what you do not. The tree can be built in rounds.
  3. Select "Finish And Save" at the bottom. Email the answers file it saves to your Cisco contact.

The questionnaire works offline. Nothing you type is sent anywhere until you email the saved file.

Part 2. Save Your Current Scope List

Do this part only if your tenant already has scopes below the top-level scope.

  1. Check that Python 3.8 or later is installed. In Terminal (macOS or Linux) or Command Prompt (Windows), run python3 --version. On Windows, use py in place of python3 in every command. When the program prints a command for you to run next, it already uses the right form for your computer.
  2. Have a Secure Workload API key and API secret ready. The key is 32 characters and the secret is 40. The key needs the capability user_role_scope_management. The long Security Cloud Control access token is a different credential and does not work.
  3. In the folder that holds csw_scope_helper.py, run: 
    python3 csw_scope_helper.py export --under "full name of the scope to build under"
    Leave off --under and the name to save every scope in the tenant.
  4. Enter your tenant address, the key, and the secret when asked. The secret is not shown as you type or paste.
  5. Email the file it saves, named like "2026-11-19 Name - CSW Existing Scopes.json", to your Cisco contact.

This command only reads. It changes nothing in your tenant, and it never saves your key or secret.

The command also reads what depends on each scope, so the plan can warn you before a scope that is in use is removed. It saves only the ID and name of each item and reads no policy content. Each list needs its own capability on the API key. If the key lacks one, the command still works and marks that list "not read".

  • Workspaces: app_policy_management
  • Inventory filters: app_policy_management or sensor_management
  • Roles: user_role_scope_management, as a site admin or an owner of the top-level scope

Part 3. Build The Scopes

Your Cisco contact sends back three things: the plan document, a label file, and a plan file. Read the plan document first. Its to-do list repeats these steps with your scope name filled in.

  1. Add to the label file if needed. You can add rows for servers the questionnaire did not cover. Keep the first column named IP and do not rename the other columns.
  2. Check the label file. This changes nothing and lists any existing value an upload would replace: 
    python3 csw_scope_helper.py check-labels --labels "your label file.csv" --under "full name of the scope to build under"
    If it says STOP, do not upload. Send the output to your Cisco contact.
  3. Upload the label file. In Secure Workload, go to Organize > Label Management > User Defined Label Upload. Choose the Merge operation.
  4. Preview the build. This changes nothing and lists every scope it would create: 
    python3 csw_scope_helper.py apply --plan "your plan file.json" --under "full name of the scope to build under"
  5. Build. Run the same command with --write added at the end, and type yes when asked. Each scope is created, read back, and confirmed. If the build is interrupted, run the same command again. It says it is continuing the earlier build and picks up where it stopped.
  6. Make approved changes to existing scopes, if the plan has any. The plan document lists them under "Changes To Existing Scopes". Creating scopes never touches them. To rename scopes or change queries, add --allow-changes after --write. To remove scopes, add --allow-removals. The program lists each change, before and after, and waits for you to type yes. Items your Cisco contact did not approve are skipped and listed. To look at the pending query changes in Secure Workload before they take effect, also add --no-commit. The program then makes the changes and leaves the commit to you, under Organize > Scopes and Inventory.
  7. Check the result. In Secure Workload, look at the new scopes under your parent scope and compare the workload count in each with what you expect.

If You Need To Reverse It

The build saves a record file and prints the exact command to reverse what it did:

python3 csw_scope_helper.py undo --record "the record file.json"

That previews the reversal. Add --write to carry it out. It removes only scopes listed in that record file, and it refuses if anything it did not create has been placed under them. If the build renamed scopes, changed queries, or removed scopes, undo puts the names and queries back and recreates the removed scopes. A recreated scope gets a new ID, so anything that was attached to the old one must be attached again by hand.

If the connection drops during a build or an undo, the program checks your tenant, records what was and was not done, and stops. Run the same command again and it continues from there. If undo says a scope is "IN USE, not removed", something was attached to that scope after it was created. Remove what depends on it in Secure Workload and run the same undo command again.

If the record file is lost, this lists every scope under your parent scope that the program created:

python3 csw_scope_helper.py undo --find-created --under "full name of the scope you built under"

That only lists them. Add --write to remove them. It asks you to type yes and repeats the number of scopes first.

What The Program Will And Will Not Do

  • It changes your tenant only when you add --write and type yes.
  • It adds new scopes under the parent scope you name. It renames, changes, or removes an existing scope only when the plan approves that item, you add --allow-changes or --allow-removals, and you type yes after seeing it listed. --yes does not skip that prompt.
  • It never changes a top-level scope or anything outside the parent scope you name. It cannot move a scope to a different parent.
  • If Secure Workload refuses to remove a scope because something depends on it, the program prints what Secure Workload says, leaves the scope in place, and does not try again.
  • It does not upload labels and does not create or change policy.
  • It commits scope changes only when every uncommitted scope change in the tenant is part of its own work. Otherwise it tells you to commit from Organize > Scopes and Inventory. A commit can take several minutes. The program waits up to 5 minutes and then keeps checking. Use --commit-timeout with a number of seconds to change the wait.
  • If your tenant is an on-premises cluster with a private certificate, add --ca-file with the certificate file. There is no option to skip certificate checking.
  • It is a single readable Python file that uses only the Python standard library. Your security team can review it before you run it.

For A Later Round

Open interview.html, select "Continue From A Saved File", add what you have learned, answer Yes to the question about existing scopes, and use "Finish And Save" again. Then repeat Part 2 and send both files.
